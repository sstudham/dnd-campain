# Spawn System standing rules - DnD

This system is a Spawn System. Its operating instructions inherit the collection's rules below. Collection authority: the Spawn Systems operating guide (`OPERATING_GUIDE.md` in the operator repo, private GitHub `sstudham/spawn-systems`). Where this system's own canon conflicts with these rules, the system's canon prevails inside the system and the conflict is recorded as an exception in the operating guide.

PUBLIC repository: no private material, secrets or personal records. Canon changes only on Scott's explicit save request.

**Spawn System standing rules (owner instruction, September 19, 2026; canonical text: `control/standing-rules-block.md` in the Spawn Systems operator repo).**
1. **Architecture-version rule.** Design, build, operate and update this system under the latest *accepted* Spawn System architecture and operating guide. Before design, release or any update, resolve the current canonical architecture and record the version/date used. Do not treat an unaccepted draft as accepted; while no version is accepted, use SCOPE.md and the system's current authority as the recorded interim and say so. Do not freeze the work to today's scope.
2. **Impact assessment.** Every future architecture revision needs a recorded impact assessment before permitted updates are made. A revision never authorizes blindly migrating protected systems or changing Prima.
3. **Owner-review hold.** Pending builds - Operations Center (project 16), Chief of Staff, Travel and PC1 system infrastructure - stay paused until Scott explicitly releases them after reviewing/debugging the Spawn Systems architecture and operator. Remediation completion, corrective-project completion, admission-list removal, dependency completion or an automatic resume is never a release. Only Scott's explicit statement releases them.
4. **Exceptions.** Unavoidable non-conformance is documented and resolved through the operating guide, never silently omitted.
